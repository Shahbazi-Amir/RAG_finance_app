# Foundation F3 APP_ONLY isolated private Docker topology: Build / Start / Restore readiness
Source expected exact Git SHA must be supplied as `F3_SOURCE_SHA` and verified against `git rev-parse HEAD`. Three app images are real Python3.13 API, Python3.13 Bootstrap and Node22 Next; no Engine lock/image/Runner/Qdrant present. PostgreSQL17.11 service has a new named volume. This file is an **installation blueprint**, not an observed Mac deployment.
## Safety / installation sequence
1. Ops obtains separate explicit authority, local source snapshot, copy checksums and names an isolated Docker project that cannot collide with `rag_finance_f3_demo`, existing volumes, or Arvan. Never use `down -v` on any existing project. Run `git diff --exit-code`, `git rev-parse HEAD`, verify manifest Git blobs and source tar/hash from approved checkout.
2. Prepare distinct UID-owned 0600 configs and 0700 directories for API(11001), Bootstrap(11002), Web(11003), and PostgreSQL service password. The TLS service certs and issuer trust must match actual cert SANs for 127.0.0.1, with an mTLS verified BFF leaf fingerprint and RS256 key. No transport trust by X-Forwarded-Client-Cert. API config has exactly `api.private_app_only_asgi.v1` keys in `F3_APP_ONLY_PRIVATE_API_BOUNDARY_20261123.md`; BFF `send_mode=DISABLED`.
3. Set all F3 variables as *environment variables*, not committed secrets; parse first: `docker compose -f infra/phase3_l1/compose.app-only.yaml config --quiet`. Build-only with `docker compose -f ... build --pull` on a separate host, then verify effective runtime UID, OCI source revision and actual base image digests (DockerHub CI tags NOT accepted).
4. Start `pg` alone, then have DB owner install exact 001–010 + DB55 and all Product/Bootstrap restricted roles in this **new** PG instance using an approved idempotent installer; the laboratory script 03 from `infra/postgres/dev_f3_isolated` is **NOT a production installer** and must never be blindly pointed at this database. Only after actual SQL ledger/ACL/TLS evidence, start API, Bootstrap, Web in order. API /health/ready must return 200 only after true PKI/role verification. API Send HTTP503 with zero durable writes; Web app-only visually disables Send.
5. This compose publishes **no public or host port**. API, Bootstrap and Web share API network namespace specifically because the verified TLS server binds 127.0.0.1. SERVER/Ops must supply and approve a distinct authenticated ingress/HTTPS endpoint in that namespace before any external browser or Login E2E. It cannot be treated as a completed production deploy. External IdP egress network requires Firewall allowlist.
6. From an independently approved fresh volume, backup with actual sha256, restore to a DIFFERENT isolated PG cluster/volume, compare schema, roles, exact 10-row ledger, owner A/B sessions and one actual signed browser-to-SQL journey. Only then measure RPO/RTO vs employer-signed thresholds. No unapproved volume deletion or 011.
7. Production/launch/Arvan HOLD and Mac demo unchanged. Engine, Source/Locator C018, Phase2/NB23 Gate00 and Gateway all separately gated. Ownership and exact external receipts in GitHub Issue #78.
## Errors / preflight
- Missing env or file: refuse start; container is unhealthy, never synthesize a pass.
- Missing Product roles or bad TLS/RS256: API fails before listen, no Send or History.
- Missing BFF config: UI fails closed; no anonymous real Product data.
- Web container has no standalone network: its server listens 127.0.0.1 in API namespace by design. It will NOT work from another network without an approved ingress.
