# ADR 0003 — permanent conversation history and message persistence (PROPOSAL)

**Status:** **PROPOSED — NEEDS_API_DB_REVIEW**, AGENT-HISTORY-01, 2026-11-07. This is *not* a DB01-02 final decision, production API acceptance, Auth approval, Migration, RLS implementation or Module Gate PASS.

- Problem: a reliable owner-scoped list/message history and recoverable send operation requires stable client and server identities, separate HTTP attempt tracing, consistent ordering/cursor and explicit crash boundaries.

## Proposed logical contract and persistence boundaries

1. **Create empty conversation** with `client_conversation_id`, separate `idempotency_key` and nullable title; short atomic insert + scoped idempotency record. Replays return the original Conversation snapshot, new current HTTP trace, without creating another Conversation. Conflict on same owner/scope/key but different canonical client payload.
2. **Send message** retains old `send_message_request/send_message_receipt` fingerprint and original requested `conversation_id` (possibly null). In **T1 atomic transaction** allocate Conversation if needed, insert one User Message and persist Receipt/Idempotency record; both commit or neither. The response Receipt proves Message persistence, **not** Answer persistence.
3. **T1→T2 durable state:** represent as `persisted` with stable `resolved_conversation_id` and User `message_id`; Attempt fields empty. Read-only status allows deterministic lookup after disconnect. It must not launch a model or create a second Message.
4. **T2 short transaction:** create `attempt_id` tied to trusted owner and initiating Receipt, record `attempt_request_id` and `attempt_trace_id`, reserve `reserved_answer_id` as correlation-only (not an Answer), commit before any future external engine call. **For user message sends, recommend required Receipt→Attempt linkage**; non-message internal run exceptions require separate design. After ambiguous crash/timeout mark `attempt_unknown` and **do not automatically retry provider/model**.
5. **T3 short transaction:** only a genuinely validated terminal result creates **separate assistant Message** and Answer and binds `answer.message_id` to that assistant Message; `answer_id=reserved_answer_id` when committed. A crash before T3 leaves Attempt/status (not phantom Answer); after T3 commit, recovery reads the *existing* Answer. `attempt_unknown→answer_committed` requires authoritative T3 DB evidence; failed/cancelled states have no fabricated Answer.
6. **Identifiers:** stable `client_message_id` vs persisted User Message ID vs assistant Message ID vs Answer ID vs Attempt ID. Each incoming HTTP/status query has a **fresh trusted `request_id/trace_id`**. Historical Attempt `request_id/trace_id` remain separate. No internal id is automatically an NB23 input.
7. **Ordering/query:** Conversation `created_at DESC,conversation_id DESC`; Message `created_at ASC,message_id ASC`; server timestamps, bounded limit 1–100 default 20, `limit+1` has-more check and owner/resource/filter-bound signed opaque Keyset cursor with first-page high-watermark. A mutable `updated_at` is unsuitable as keyset order. Validate expiry/tampering/owner/query mismatch and reauthorize every page. Cursor signing secret lifetime and TTL remain open.
8. **Isolation:** authenticated server context (not client owner) gates all queries; read/write Owner predicates, RLS and relationship FK checks required in future DB task. Nonexistent/foreign or inaccessible IDs must be externally indistinguishable 404 without owner leakage. No unauthenticated/fixed-user production identity. Actual Auth/CSRF/session lifecycle is a separate employer decision.
9. **Deletion:** use existing `delete_command/delete_status`; suppress deletion-requested Conversations from ordinary list. Soft/hard deletion, Retention, backup and post-deletion access remain open; Export remains independent.
10. **Physical constraints to review:** uniqueness with nullable original `requested_conversation_id`, lock/CAS and concurrent first-send, transaction isolation and abort behavior, immutable hash/dedupe, TTL/collision/reuse horizon, Attempt lease/reconcile and crash/outbox policies, User/Answer foreign keys, owner-scoped joins and RLS. **No SQL/DDL or migration is authorized in this proposal.**


## Bounded supervisor baseline for isolated synthetic PostgreSQL tests (HST-01-D)

**Approval boundary:** the supervisor has chosen these **logical invariants only for the first isolated synthetic PostgreSQL test package**. They are *not* decisions on Auth provider, production endpoint, PostgreSQL version, DDL/index syntax, Retention, Migration, model invocation or full DB01-02/M04 Gate. Existing ADR sections remain historical proposals; this section narrows the testable subset. Treat unresolved physical implementation as `NEEDS_API_DB_REVIEW`.

1. **Independent Create/Send identities:** Create uses `(trusted_owner, operation=create_conversation, client_conversation_id, idempotency_key)`; Send uses `(trusted_owner, operation=send_message, original_requested_conversation_id [including literal null], client_message_id, idempotency_key)`. These *logical scope keys and fingerprints* are not interchangeable. A resolved ID allocated during T1 never silently replaces the original requested null in the replay scope. Same scope/same payload returns the original durable receipt; same scope/different fingerprint yields 409 without a new row. Different users and operation types are isolated.
2. **At most one Attempt per accepted Send operation in this package:** T1 commits **one** scoped Receipt, Conversation allocation (if null) and immutable User Message; T2 separately commits **zero or one** Attempt, bound to that same valid owner-scoped Send Receipt. A Send may remain `persisted` (T1 only) with zero Attempts. Two concurrent T2 dispatchers must resolve to the same Attempt or one must fail closed; a network retry is *read/replay only* and cannot insert another Attempt or trigger a provider. T3 alone commits a verified final Answer plus a different assistant Message. T1/T2/T3 are separate short transactions. **No automatic model run/re-run or second Attempt** is allowed in this first package; future explicit multi-Attempt / engine retry policy is outside scope. Do **not** delete, normalize, reparent or rewrite historical Attempt rows. If legacy rows already show multiple Attempts for one Send Receipt, preserve them, flag an integrity anomaly and stop new scheduling / return a generic temporary-unavailable response until an explicit DB review; never silently choose one to overwrite.
3. **Immutable Create receipt snapshot versus current authorization:** T1 stores the *original creation Conversation snapshot* (or immutable creation-event equivalent) in a separately durable Receipt relation. A subsequent title, status or metadata update does not rewrite that original snapshot. On `replayed`, authenticate the current server actor and check the Conversation **current** owner, existence, visibility and active/access-allowed state using a coherent authorized read *before* revealing the immutable snapshot; apply non-enumerating generic **404** for a deleted, deletion-requested, inaccessible or foreign Conversation. A replay of a deleted operation neither resurrects nor creates a new Conversation, and must never leak its previous title/content or cross-user existence. Serialize the access check with relevant deletion/state changes in the future DB design; retention duration, eventual hard deletion and post-account-revocation policy remain open.
4. **NULL and concurrent Send uniqueness:** the DB must enforce uniqueness of the **original requested nullable conversation identifier as a logical value**, including the case `requested_conversation_id = NULL`, scoped to trusted owner + send + client_message_id + idempotency_key. A normal PostgreSQL UNIQUE over nullable columns alone is not accepted without explicit NULL semantics. Actual `NULLS NOT DISTINCT` (version dependent), partial indexes or canonical non-null discriminator, transaction isolation and locking/CAS are **DB implementation choices** requiring an explicitly selected PostgreSQL version and real concurrent positive/negative tests. Atomic T1 must prevent duplicate Receipt/User Message/Conversation allocation; atomic T2 must prevent duplicate Attempt; atomic T3 must prevent duplicate Answer and assistant Message. Unique DB persistence does **not** imply exactly-once model execution.
5. **Server-origin commitment evidence / coherent status read:** a final `answer_committed` or a reconciliation out of `attempt_unknown` must be derived solely inside trusted API/DB code from committed, owner-authorized Receipt + Attempt + reserved ID + terminal outcome + Answer/assistant Message rows linked in **one consistent database snapshot** (one transactional read or equivalent), not from any client-provided evidence, header, boolean or JSON. The `server_commit_evidence` dict in synthetic `history_semantics.py` is a *test-only witness*, not an API wire field or transferable proof. Preserve original T2 `attempt_request_id/attempt_trace_id` and use fresh current lookup `request_id/trace_id` independently; no mixed T1/T2/T3 values from different DB snapshots. Read-only Recovery/Polling never invokes a model. Transaction isolation/revision/replica-routing strategy must be tested and agreed with DB/API owners; no specific physical isolation is frozen here.
6. **Polling and revision limitation:** sparse polling may skip observed states, **not persisted T1/T2/T3**. Older-issued late HTTP responses must not roll back the UI; newer-issued regressions must be reported/rejected. The client's issuance sequence is **not** a trusted server commit order: a later request may hit a stale replica or inconsistent read. Until an authoritative monotonic server revision or primary/consistent-read policy is reviewed, these UI checks alone cannot prove backend monotonicity. Do not invent a revision field, change the provisional wire schema or call a model while reconciling.

## Auth choices for employer (not enabled)

- **Option A — recommended for evaluation:** standards-based managed OIDC / Authorization Code+PKCE with backend-for-frontend session. Needs vendor/data residency agreement, redirect security, session binding, revocation/consent and MFA policy. **Cost:** possible recurring per-active-user/provider fees plus integration/operations. **Security:** avoids storing application passwords but adds provider, redirect and token-handling risks. No vendor/plan/price authorized.
- **Option B — alternative:** first-party credential processing and server-side sessions. Needs secure password hashing, MFA, verified recovery/reset, brute-force protection, CSRF/session rotation, audit and human operations owner. **Cost:** no mandatory IdP subscription but higher ongoing engineering/security/support burden. **Security:** reduces identity-vendor transfer but materially increases breach/credential responsibility.

**Recommendation:** obtain employer decision on A vs B plus owner mapping, data residency, session expiry/revocation, post-account-deletion status and threat review **before** implementing live Auth/API/DB. Production fixed/anonymous user bypass is prohibited.
