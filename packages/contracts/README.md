## Product-level invariants beyond JSON Schema

The runnable cross-checks reject orphan/duplicated claim/citation IDs and asymmetric **two-way** links, answer-to-assistant-message mismatch, cross-user snapshots, feedback for an unknown answer, unauthorized pagination results, skipped or duplicated event sequences, missing/repeated terminal events, synthetic source verification and inconsistent request receipts. These checks are **local synthetic contract checks**, not live services, database RLS tests, or real source accuracy tests.

**Attribution:** `credited_author_name`, `editorial_supervisor_name` and `speaker_name` are separate nullable fields. `content_authority_type`/`attribution_status` do not authorize inventing identity, page, URL or timestamp. For `SYNTHETIC` examples, citation `resolution_status=unresolved` and `locator=null` remain mandatory for honest evidence labeling, but **known or hypothetical source metadata may be present** with `attribution_status=unknown`. Synthetic data must **never** be presented as verified locator or attribution evidence. Verified source attribution requires independent provenance, even if an unresolved entry already contains names or a source identifier. Future `verified` source claims require independent server-side provenance and actual resolver checks; schema acceptance alone is insufficient. `speaker`/`speaker_name` mapping to NB23 is pending.

**Confidence:** `null` means **unmeasured**, not a measured value of zero. If a value is genuinely measured, it must be an object with `value` in `[0,1]` plus nonempty `meaning` and `calibration_scope`. A synthetic example with numeric value is not evidence of actual calibration.

**Answer status:** `error` is a technical failure (`state=failed`, error object and no successful claims); `no_answer` is an ordinary abstention (`state=completed`, `error=null`); `partial`, `unknown` and `cancelled` remain distinct. Never transform an unknown backend state into completed or no-answer. A partial answer is not fully validated success.

## Send-message idempotency policy — no Exactly-once model claim

1. The request comes without a trusted identity. Server derives the **authenticated principal** independently, then scopes the idempotency record by `(trusted_user, operation=send_message, requested_conversation_id, client_message_id, idempotency_key)`. A null `requested_conversation_id` for a new thread stays **null** on the original request/retry; the new server-assigned `resolved_conversation_id` must never be substituted into its idempotency scope.
2. Server computes `payload_sha256` over the exact UTF-8 bytes of JSON with **only** `client_message_id`, `requested_conversation_id`, `question`, sorted keys, compact separators `(',',':')`, `ensure_ascii=False`, no Unicode case/whitespace normalization. The server does not trust a client-provided hash.
3. First request persists one `created` receipt. Same authenticated scope/key and same fingerprint returns `replayed` with the **same persisted `message_id` and `resolved_conversation_id`**. Successful `created`/`replayed` receipts must contain non-null resolved IDs; on `conflict`, both `message_id` and `resolved_conversation_id` are null. Changed canonical payload under the same scoped key returns `conflict`, no message ID and an explicit validation error (the HTTP status mapping is a separate API decision). Same key in a *different authenticated user scope* is independent.
4. This policy is for **duplicate message persistence/receipt and safe client retry**, **not** a guarantee of exactly-once model/provider execution, server cancellation, transaction retry or external side effects. API, DB and Foundation must agree on transaction boundary, commit/abort, authorization, timeout handling and stable error mapping before runtime integration.

## Streaming and cancellation — proposed events, not provider facts

- `connected`, `retrieving`, `generating`, `delta`, `cancel_requested`, `display_cancelled`, `server_cancelled`, `completed`, `failed`, `unknown`. `retrieving`/`generating` require actual `reported_by=backend`; a frontend must not infer these as internal engine phases merely because it displays a spinner.
- `completed`, `failed`, `server_cancelled`, `unknown` are mutually exclusive **terminal server-result events** for the consumer stream. A complete session has **exactly one final terminal event**, no events after it, contiguous sequence starting at 0 and matching stream/answer/request/trace IDs. `unknown` is a reported *unknown state*, not a proven server success/failure; recovery contract remains provisional.
- `display_cancelled` means **UI display stopped only**. `cancel_requested` means a server stop was *asked for*, not proved. Only `server_cancelled` with explicit server report (`server_stopped=true`, confirmation reference) claims the server stopped; it requires a prior cancel request. A display-cancelled stream does not imply provider execution stopped. Event schemas and recovery algorithm remain `provisional/blocked_by=NB23` for live producer integration.

## Deletion, pagination and trust

- Frontend requests account/conversation deletion with explicit confirmation; successful API dispatch is **not** successful deletion. `delete_status.succeeded` requires `backend_confirmed=true` and completion time; further cache/backup/retention obligations are policy decisions, **not** claimed as implemented.
- A cursor is opaque and cannot authorize another user's data. Source of trusted `owner_user_id` is the backend-authenticated principal (method/provider still undecided), never a user-supplied request field.
- Export availability and policy are **unresolved**, but the deletion contract is independent. Retention duration remains undecided.

## Reviewed correction set — product.v1 regression.1 (still PROVISIONAL)

### CT-FIX-01 — exact delta reconstruction (P3M13/14)

- `stream_event.event_type=delta` now requires `data.text` to be a **nonempty string**, allowing `" "`, `"\\n"` and other whitespace-only chunks without trim, normalization or dropping content.
- This exception applies **only** to `delta.data.text`; final `answer_text` still requires visible non-whitespace content.
- The synthetic stream-session regression concatenates `["سلام", " ", "دنیا", "\\n", "خط دوم"]` to the exact string `"سلام دنیا\\nخط دوم"`. Terminal, cancellation and ordered-sequence checks remain mandatory.

### CT-FIX-02 — requested versus resolved conversation identity (P3M03/10/13)

- **Client request:** `requested_conversation_id` is a non-null existing conversation ID or `null` for a new conversation. The prior ambiguous client field `conversation_id` was **renamed**; this provisional-breaking change requires coordinated API/UI/DB review before any freeze.
- **Server receipt:** `requested_conversation_id` repeats that original client value, while `resolved_conversation_id` is the **server-assigned stable conversation ID** for successful `created` or `replayed`. `message_id` must also be stable. A `conflict` has both resolved ID and message ID set to `null`, with an explicit error.
- **Existing thread:** resolved conversation must equal non-null requested conversation. **New thread:** requested stays `null`, resolved is non-null. This distinction is checked by Schema **and** `check_request_receipt` / `check_idempotency_history`.
- **Fingerprint:** computed over the original immutable request fields `client_message_id`, `requested_conversation_id`, `question` in deterministic sorted UTF-8 JSON. Persisted receipt scope uses the same original requested ID. A later server allocation does not create a new idempotency scope, and retry returns both original IDs. Changed payload under the same scope remains a conflict; trusted identity is server-sourced and user scopes remain separate.
- No claim of exactly-once execution of model, provider or any external side effect.

### CT-FIX-03 — typed locators, anchors and independent source metadata (P3M11/14; M00 remains blocked)

- `source_attribution.source_type` is explicit: `website | book | transcript | null`; `null` is allowed for genuinely unidentified unresolved sources.
- `locator.kind=url` requires HTTPS for a website. Existing `book_page` (positive page) and `transcript_timestamp` (nonnegative known milliseconds) forms remain valid for their matching source type.
- New `book_anchor` requires nonempty `work_id`, `edition_id` and stable `anchor` with `page=null`, `timestamp_ms=null`; new `transcript_segment` requires `episode_id` and `segment_anchor` with `timestamp_ms=null`. No guessed page `0` or made-up timestamp is used to fill missing data.
- Mismatched `source_type` and Locator kinds, incompatible extra fields and missing anchors are rejected by Schema.
- `resolution_status=unresolved` means **locator is not resolved** but may retain known `source_id`, `source_type` and distinct author/editor/speaker names. `attribution_status` represents separate verification, not a side effect of locator resolution. Synthetic answer provenance rejects **either** verified locator or verified attribution; metadata examples are explicitly hypothetical and never evidence of a real source.

## CT-09 — Feedback submit/receipt: provisional, server-confirmed

**Cross-reference:** UI-09, DB01-11/12; P3M03 (Product contract), P3M13 (Application API), P3M15 (Feedback/history), P3M06 (user isolation).

- **Client-only `feedback_submit_request`:** `client_feedback_id`, `conversation_id`, `answer_id`, `rating`, optional-null `reason`, and `idempotency_key`. The browser **must not** send `owner_user_id`, `request_id` or `trace_id`. No Auth mechanism or feedback-edit/multi-feedback rule is selected.
- **Server-only `feedback_submit_receipt`:** `owner_user_id` from verified server actor context, server `request_id`/`trace_id`, `client_feedback_id`, `conversation_id`, `answer_id`, scope `trusted_user+submit_feedback+answer`, `payload_sha256`, disposition (`created | replayed | conflict`), nullable `feedback_id`, nullable `persisted_at`, nullable error. **Created/replayed require non-null persisted ID/time and no error; conflict requires null ID/time and explicit error.**
- **Recorded `feedback`** remains distinct: the receipt is an acknowledgement of actual server persistence, not merely UI dispatch. `check_feedback_request_receipt` compares actor, request, receipt, optional persisted feedback document and optionally a trusted conversation snapshot/answer ownership. The server must still do real authorization and storage checks; local synthetic snapshot validation is not RLS proof.
- **Feedback Trace binding (created / replayed / conflict):** each server-generated `feedback_submit_receipt.request_id` and `.trace_id` refers to the **current HTTP/network attempt** and **must individually equal** the `request_id` and `trace_id` on that attempt's trusted `server_auth_context` (`check_feedback_request_receipt`). The client cannot supply these fields. For `created`, mismatched request or trace is rejected even when the owner and feedback target match. For `replayed`, a **new retry may have new server-minted request/trace IDs**, and the receipt must echo **those current** IDs, **not** blindly repeat the original attempt's IDs. Stable `feedback_id` and `persisted_at` always refer to the **original persisted Feedback record**: `check_feedback_receipt_history` requires them unchanged across a replay, but does not require identical network-attempt traces. A replay cannot claim new persistence or exactly-once model/provider execution. This is a provisional product rule; authentic server context still requires actual backend authorization.
- **Retry:** server computes SHA-256 over stable original `client_feedback_id`, `conversation_id`, `answer_id`, `rating`, `reason` as sorted compact UTF-8 JSON. Exact retry under the same authenticated user+answer+client ID+key returns identical persisted `feedback_id` and time. Different payload under the same scope yields conflict without claiming success. The same key under a different authenticated user is isolated. No exactly-once provider, message, or feedback side effect is guaranteed by Schema alone.
- **Disconnected client:** unknown delivery is a **local UI state**, not a server receipt disposition or confirmation of success; retry/reconciliation uses the same immutable original payload. HTTP status/expiry, feedback edits and policy for multiple records remain **open**.

## CT-10 — Deletion request, server context and protected status lookup

**Cross-reference:** UI-13, DB01-13; P3M03, P3M15, P3M21. This is a **provisional-breaking** adjustment of `product.v1` draft fields, not a frozen interface.

- **Client `delete_command`:** `client_action_id` (client-owned stable retry/correlation ID), `deletion_scope`, `conversation_id` and `confirmed_by_user=true`. Removed `request_id` and `trace_id` from the **client wire document**; untrusted clients cannot choose server traces or owner.
- **Server `delete_status`:** server-minted `deletion_request_id`, `request_id`, `trace_id`, authenticated `owner_user_id`, echoed `client_action_id` and matching scope/conversation, real server state (`requesting | processing | succeeded | failed`), timestamps, confirmation and error. Submission alone is not deletion; `succeeded` requires backend confirmation plus completion time.
- **Client `delete_status_query`:** minimal `deletion_request_id` and `client_action_id` correlators, **not credentials**. The backend MUST authenticate/authorize each lookup against the trusted owner and prevent cross-user disclosure/enumeration. `check_delete_command_status` and `check_delete_status_query` exercise cross-document ownership, action correlation and server trace distinction only; they do not implement Auth.
- **Transport interruption:** `unknown` belongs only to UI/local transport tracking, **not** `delete_status.state`. Never present an unconfirmed request as success. The validity of polling an **account deletion after the session has been revoked** requires a separate, security-reviewed Auth decision: no anonymous operation-ID lookup is implied or authorized.
- **Export** is independent of deletion; no Retention term, backend policy, post-deletion reauthentication or authorization scheme is chosen.

## CT-12 — Receipt / Attempt / Message / Answer persistence lifecycle

**Proposal status: `NEEDS_API_DB_REVIEW`**. **Documentation only**: no SQL/DDL, migration, backend implementation, provider call or physical constraint is authorized. Maps: P3M04 (PostgreSQL data model), P3M10 (orchestration/idempotency), P3M13 (API transport), P3M15 (history); DB01-04A/10A, UI-02/05/09/10.

| Stage | Proposed short-lived boundary | On success / crash behavior |
|---|---|---|
| 0 — Trusted ingress | API authenticates actor **outside untrusted payload**. Retain immutable `requested_conversation_id`, `client_message_id`, key and canonical `payload_sha256`; validate owner and conversation access | Replays use **original requested ID**, not newly allocated conversation ID; a key/payload conflict returns explicit conflict without new Message. |
| T1 — Receipt + user Message | **Short DB transaction:** atomically acquire/insert scoped Receipt, allocate new Conversation ID if requested is null, insert the user Message once, store `resolved_conversation_id`, stable `message_id`, request/trace references and commit. Existing committed Receipt is replayed without duplicate Message | Crash **before T1 commit:** abort/rollback; retry may create the initial receipt. Crash **after T1 commit but before HTTP acknowledgement:** retry returns stable persisted ID(s), not a second Message. A created receipt proves message persistence, **not** an Answer. |
| T2 — Execution Attempt start | New independent `execution_attempt` persisted in another **short transaction** with trusted owner, attempt ID, `request_id`, `trace_id` and, when securely available, optional Receipt linkage; record `started/pending` before any external execution. **Reserve `answer_id` here** solely as a stable stream correlation ID, not an Answer row or success | Crash before T2 commit: T1 Receipt/Message remain, no Attempt. Crash after T2 commit: Attempt/trace remain even if no Answer is ever stored. Whether all product attempts must require Receipt linkage remains **API/DB review pending**. |
| Outside transaction — Model/retrieval | API invokes permitted runtime separately; **never hold a PostgreSQL transaction open during model execution**. Link retrieval/model traces to Attempt; `answer_id` remains a reservation, not a final Answer claim | Timeout/crash/provider ambiguity: preserve Attempt as failed/cancelled/unknown via a later short status transaction, **without an Answer**. Server-stop and display-cancel semantics stay distinct. Exactly-once provider execution cannot be inferred. |
| T3 — Finalize | **Short DB transaction:** only after a valid terminal result, insert the Answer (and assistant Message/claims/citations if applicable), atomically bind it to the reserved `answer_id` and Attempt and mark Attempt terminal; commit, then acknowledge/stream final status | Crash **before T3 commit:** rollback Answer/assistant Message, preserve earlier Attempt/Receipt and recover as unknown/failed as evidenced. Crash **after T3 commit but before HTTP response:** replay/query retrieves existing finalized output; do not duplicate Answer/Message. |
| Failure/cancel finalization | Separate short transaction updates Attempt's terminal status and redacted error/trace; no Answer row is mandatory for failed/cancelled attempts | `request_id`/`trace_id` and Attempt evidence remain even when `answer_id` was reserved but no Answer was committed. Unknown must not be silently reclassified as no-answer or server-cancelled. |

**Decision notes:** Choosing to reserve `answer_id` at T2 reconciles provisional `stream_event.answer_id` with no preexisting Answer; it is **not** final Answer persistence. Replayed message Receipt, process Attempt, provider execution and Answer are different lifecycles. Recovery requires a durable status/lease policy and appropriate owner checks. Physical Unique/NULL handling for `requested_conversation_id=null`, locking, the idempotency TTL, status recovery, exact commit boundaries and whether Attempt requires Receipt are deliberately **OPEN**; no exact-once engine guarantee or fixed DB approach is selected.

**DB owner reconciliation required — do not edit DB files here:** the reviewed DB ERD at `75fed8ba07efd5619ef1cc5de5d445afabccca0c` shows `message_request_receipts |o--o| conversations`, which implies at-most-one Receipt per Conversation even though **one Conversation may have many Receipts**. Its `message_request_receipts ||--o{ execution_attempts` relationship implies every Attempt belongs to a Receipt, while the Dictionary has `receipt_row_id?` optional. DB owner must make the ERD and Dictionary consistent, then jointly review the physical transaction/identity/answer reservation plan with API.

### Identity, ordering, cursor and message/answer linkage

- **Trusted ownership:** every write/read/status requires freshly validated server actor `trusted_actor_context`, scoped to the authorized owner's rows. Ignore/reject all client-supplied owner fields; request/trace IDs are minted for each HTTP attempt, **not** obtained from caller's body or trusted merely because the caller knows an object ID. All inserts, joins, RLS and FK reviews must be owner-bound, and cross-user/missing IDs must be indistinguishable externally. Synthetic tests use **only test actor fixtures**, never a fixed production user or anonymous endpoint.
- **Conversation order:** `(created_at DESC, conversation_id DESC)`, **not** mutable `updated_at`, so message updates do not shuffle earlier keyset pages. Exclude `state=deletion_requested` from ordinary list. **Message order:** `(created_at ASC, message_id ASC)`, using server-assigned timestamps and immutable IDs; no offset pagination or duplicated/missing row on timestamp ties. The first page fixes an upper-watermark `anchor`, subsequent pages use exclusive `last` key. New records after that anchor appear only on a new first-page session; deletion may remove rows without leaking another owner's rows.
- **Limit:** 20 default, 1–100 after server normalization; fetch `limit+1` rows to compute `has_more`. `page.next_cursor=null` iff `has_more=false`. Cursor must be opaque, authenticated (HMAC or equivalent), versioned, owner/resource/conversation/query-limit/anchor/last/expiry bound, bounded in size and reject tampering, cross-user use and expired tokens. `history_semantics.make_test_cursor/verify_test_cursor` are **test-only contract references with caller-supplied key**, not production signing or a substitute for Auth. Secret storage/rotation and actual cursor TTL remain **NEEDS_API_DB_REVIEW**.
- **Different identities:** `client_message_id` is a stable client retry correlate; `message.message_id` identifies a persisted **user or assistant** Message; `answer.answer_id` is the durable Answer identity only on T3; `answer.message_id` identifies its distinct **assistant** Message. The user Message is **not** `answer.message_id`. `attempt_id` identifies each execution attempt and may exist without an Answer. T2 `reserved_answer_id` is **not** an Answer row or an assertion of model success. `message_request_status.request_id/trace_id` are the **current status HTTP lookup**; `attempt_request_id/attempt_trace_id` identify the actual earlier attempt and must not be overwritten by retry/query. `answers[]` in a page contains exactly the Answers attached to assistant Messages in that page, not orphans or fabricated sources.
- **NB23 isolation:** display of prior messages does **not** change upstream NB23 Draft input. Only `contract_version` and `question` have been confirmed as Draft producer inputs; history, filters, user IDs, Conversation IDs, source anchors or Attempt metadata must **never automatically** be injected into NB23 requests. L2/engine adapter remains BLOCKED by Module 00 acceptance.

### Idempotency, durable recovery, Crash and T1/T2/T3 proposal

**All decisions below remain `NEEDS_API_DB_REVIEW`; no actual PostgreSQL, Migration, RLS or provider execution occurred.** Maintain two distinct scopes:

1. **Create empty conversation:** key `(trusted_owner, create_conversation, client_conversation_id, idempotency_key)`; fingerprint SHA-256 of canonical sorted compact UTF-8 JSON containing original `client_conversation_id,title`, not owner/header/trace. One short atomic insert transaction persists the idempotency record and Conversation. Replay returns the **original persisted Conversation snapshot** under new current request/trace; same scope plus different title/fingerprint is conflict with **no new insert**. Exact DB key isolation/NULL/TTL reviewed with DB owner.
2. **Send Message:** existing `(trusted_owner, send_message, requested_conversation_id, client_message_id, idempotency_key)` and existing canonical fingerprint of original `client_message_id,requested_conversation_id,question`. **T1:** short DB transaction allocates Conversation if requested null, locks/creates scoped receipt, inserts one user Message and commits together. Crash pre-commit → no visible T1; post-commit → status/replay returns same Message and resolved ID, never a second user Message.
3. **T1 → T2 gap:** persist `status=persisted`, **both conversation/message IDs non-null and Attempt fields null**. This is a real recoverable state, not a missing or newly allocated Message. Status query reads it without side effects. **No background or HTTP retry may silently launch model execution** just because there is no Attempt.
4. **T2:** a **second short transaction** creates `attempt_id`, trusted `attempt_request_id/attempt_trace_id`, explicitly linked scoped Receipt (recommended REQUIRED for product send path; generic internal attempts may be exempt only with separate decision), reserves `reserved_answer_id`, records `attempt_pending` and commits **before** any future model call. Never hold DB transaction across external model execution. A crash/timeout/ambiguous provider status becomes `attempt_unknown`; no Answer is claimed, and auto retry **does not** invoke the model again.
5. **T3:** after an authentic, validated final result, one short transaction atomically persists Answer, separate assistant Message and their linkage, and moves status to `answer_committed` with `answer_id=reserved_answer_id`. Crash before T3 → rollback Answer/assistant Message; retain T1/T2 and reconcile unknown. Crash after T3 before HTTP response → status returns the **same committed Answer**, no duplicate Message/Answer/provider invocation. Failed/cancelled status persists Attempt and redacted error without a phantom Answer. Recovery from `attempt_unknown` to `answer_committed` is allowed **only** by authoritative committed T3 DB evidence, never an inferred successful model response.
6. **Concurrency/TTL/physical keys:** propose DB-unique operation scopes using a normalized canonical nullable-requested-ID discriminator or partial expression index (PostgreSQL NULL semantics must be tested), row locking/CAS for concurrent writes, immutable fingerprint and status transitions, and owner-scoped lookup. The **actual** index expression, TTL (including effects on retries after expiration), retention, outbox/lease/dead-letter and cleanup strategy are **not selected**. Exactly-once **persistence within a scoped DB transaction** is not exactly-once model/provider execution.

**Status invariants:** `not_found` (internal), `persisted` (T1 only), `attempt_pending`, `attempt_unknown`, `answer_committed`, `failed`, `cancelled` are distinct. The schema forbids an Answer on non-final statuses; the cross-document tests also check original requested-null vs allocated ID, owner, current vs attempt Trace, correct final Answer linkage and allowed transitions. An `answer` with `outcome=unknown` is still structurally permitted by the earlier provisional schema; the proposed **history persistence path will not synthesize one** from uncertain Attempt status, pending API/DB compatibility review.

**Deletion/Retention:** history read/list rejects foreign or `deletion_requested` rows. Actual conversation deletion is governed by the existing `delete_command/delete_status/delete_status_query` contract and open [Retention/Export decisions](../../coordination/open_decisions.md). **No retention period, soft/hard deletion policy or post-account-revocation lookup is frozen**. Export scope is not a prerequisite for legitimate deletion, but is independently pending.
